# Scalability-Fit-Review — התאמה לעומס בלי הנדסת-יתר

## ייעוד
לוודא שהמערכת בנויה כך שגדילה לא תדרוש בנייה מחדש — בלי לבנות היום תשתית לעומס שלא קיים.

## מתי משתמשים
- כל הצעה שמוסיפה רכיב, שירות, תור, cache או תלות חיצונית.
- כל טענת "חייבים X בשביל scale" — לאמת מול רמות העומס בפועל.

## קלט נדרש
- ההצעה הנבחנת.
- `docs/architecture/` · `docs/environments.md` · `docs/mvp-scope.md` · `docs/decisions-log.md` · `docs/project-status.md`.
- רמות העומס של הפרויקט — כפי שהוגדרו ב-`docs/mvp-scope.md` או ב-`docs/architecture/`.

## שלבי עבודה
1. סווג מול שלוש רמות העומס של הפרויקט:
   - **רמה 1 — השקה / פיילוט** (לדוגמה: עשרות משתמשים, פעולות בודדות ביום).
   - **רמה 2 — אימוץ ראשון** (לדוגמה: מאות משתמשים בחודשים הראשונים).
   - **רמה 3 — צמיחה** (לדוגמה: אלפים ומעלה, שפות או שווקים נוספים).
   אם המספרים של הפרויקט לא הוגדרו — **אל תמציא**: עבוד עם שלוש הרמות כמסגרת יחסית, ופתח שאלה ב-`docs/open-questions.md`.
2. לכל הצעה: באיזו רמה היא נדרשת באמת? מה קורה אם דוחים אותה — האם המעבר אחר-כך הוא החלפת מימוש מאחורי ממשק (זול), או שכתוב (יקר)?
3. **הכלל:** מה שזול להחליף אחר-כך (בזכות Mock-First וממשקים) — נבנה פשוט עכשיו; מה שיקר להחליף (סכמת נתונים, חוזי API מול מערכות חיצוניות, מודל ההרשאות, מזהים) — מתוכנן כבר עכשיו לרמה 3.
4. עלות: עלות חודשית, ומגבלות של תוכנית חינמית (שירות שנרדם, תקרות, מכסות) — הן חלק מהבדיקה, לא הערת שוליים. קודם חינם; "עובד" מוגדר במספרים לפני שמשלמים.
5. סמן single points of failure שרלוונטיים כבר ברמה 1 (לדוגמה: שירות חיצוני לא זמין ⇦ מה קורה לעבודה שכבר נשלחה אליו).

## פלט מוחזר (לצ׳אט בלבד)
טבלה: **הצעה | נדרש מרמה | עלות דחייה (החלפה / שכתוב) | עלות חודשית | פסיקה מוצעת (עכשיו / נדחה 🟢 / מיותר) | נימוק.**

## טעויות שה-Skill מונע
- בניית תשתית לאלפי משתמשים ביום שיש עשרות.
- ההפך: סכמה או חוזה API שצריך לשבור אחרי חודשיים.
- "עוד רכיב קטן" שהופך את המערכת למבוזרת בלי סיבה.
- תשתית בתשלום שנבחרה לפני שהוגדר מה נחשב "עובד".

## חסימות (Hard Rules)
- **פלט לצ׳אט בלבד** — Skill זה אינו יוצר, אינו משנה ואינו מוחק שום קובץ, בכל רמת עצמאות. הכתיבה לקבצים היא של הסוכן הראשי בלבד.
- **שלב העבודה — לפי `docs/project-status.md`.** מעבר לשלב הבא רק באישור מפורש שיירשם ב-`docs/decisions-log.md`.
- **כל תוצר חוזר לסוכן הראשי (`agent-manager`)** — נקודת התקשורת היחידה; אין ערוץ עוקף לבעל הפרויקט או בין סוכנים.
- **ההחלטה הסופית היא תמיד של בעל הפרויקט** — ה-Skill ממליץ בלבד; אסור להשתמש בו כדי לאשר, לנעול או לעקוף אישור. רכיב בתשלום או ספק חיצוני — רק באישורו.
- תחום מוקפא ⇦ **החזר הודעת חסימה במקום תוצר**.

## שפת סימונים ומדרג נעילה
- **סימונים:** ⚖️ דורש ייעוץ משפטי / נוסח משפטי — placeholder בלבד עד נוסח מיועץ · 🔧 פתוח טכנית — approach בלבד, אין הכרעה · 🟢 נדחה לשלב מאוחר (לא חוסם עכשיו) · ⛔ חסום / מוקפא — לא נוגעים עד אישור · ✅ נסגר/נענה · ⚠️ אזהרה/סיכון.
- **מדרג נעילה:** `chat-only` (נאמר בשיחה, לא אושר) → `readiness-direction` (כיוון עבודה, לא נעול) → `owner-approved` (בעל הפרויקט אישר במפורש) → `final-locked` (נעול; פתיחה מחדש = החלטה חדשה ביומן). ללא רמת נעילה — זו לא החלטה, זו שיחה.
- אסור להציג פריט ברמה נמוכה כאילו הוא ברמה גבוהה יותר. כל פריט בפלט מסומן ברמתו.
