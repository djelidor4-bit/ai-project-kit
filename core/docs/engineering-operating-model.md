# מודל העבודה ההנדסי — הקו המנחה

> **מה זה:** איך הפרויקט עובד כמערכת הנדסית: מה נשמר ב-Git, מה במקור המשימות, איך נראה ספרינט, מתי משימה גמורה,
> מה מותר בלוג ואיפה יושב סוד.
> **מעמד:** מחייב מיום התקנת הערכה (השורה הראשונה ב-`docs/decisions-log.md`). שינוי במסמך הזה = החלטה חדשה ביומן.
> **מקור:** מבוסס על 'תוכנית תפעול הנדסית ל-MVP'. כאן הוא מותאם לערכה כללית, עם לקחים מהפעלה אמיתית.
> כל מקום שבו המסמך נבדל מהמקור מסומן ומנומק.
> **קשרים:** `AGENTS.md` (החוקה, רמת העצמאות, הצוות) · `docs/environments.md` · `docs/adr/README.md` · `docs/runbooks/local-setup.md`.
> אם מותקנים: `docs/jira-workflow.md` (מודול `jira`) · `docs/prompts-and-json-governance.md` (מודול `ai-product`).

⏳ למלא: התאמות של הפרויקט הזה. כל סטייה מהמסמך נרשמת כאן בשורה אחת ובשורה ביומן, עם נימוק.

---

## 1. בשורה אחת

**Git מחזיק את מה שהמערכת היא:** קוד, prompts, JSON, חוזים, החלטות ותיעוד. **מקור המשימות מחזיק את מה שהצוות עושה:**
ספרינט, משימות, באגים ובעלים. מקור המשימות הוא Jira כשמודול `jira` מותקן ומחובר, ואחרת `docs/tasks.md`. ההגדרה ב-`AGENTS.md`.
כל שינוי קטן, עקיב והפיך, והוא גמור רק לפי ה-DoD (§9).

## 2. ששת העקרונות — כלשון המקור, מחייבים

1. Git = מקור האמת לתיעוד הנדסי, prompts, חוזי JSON והחלטות טכניות.
2. מקור המשימות (Jira או `docs/tasks.md`) = מקור האמת לביצוע: ספרינטים, משימות, עדיפויות, blockers ובעלות.
3. אחסון מסמכים חיצוני (לדוגמה: Google Drive) משמש רק לחומרים עסקיים זמניים, למסמכים משפטיים ולקבצים חיצוניים שלא נכון לשמור ב-Git.
4. Prompts ו-JSON הם נכסים הנדסיים: הם ב-version control ועוברים review.
5. כל החלטה טכנית משמעותית מתועדת.
6. שינויים קטנים, עקיבים והפיכים.

## 5. תיעוד

### 5.1 המבנה

- `docs/{adr,architecture,runbooks,product,data}/`. בכל תת-תיקייה יש `README.md` שמסביר מה נכנס אליה.
- **מסמך חדש נולד בתת-התיקייה שלו.** מסמך קיים בשורש `docs/` נשאר במקומו. הזזה שוברת הפניות בהגדרות הסוכנים, בהערות קוד
  ובמסמכים אחרים, ובמאגר שבו push = deploy גם תיקון הערה הוא פריסה.
  - מסמך ביקורת חד-פעמי עובר לתת-תיקייה כשנוגעים בו.
  - מסמכי הניהול נשארים בשורש: `00_Index` · `project-status` · `decisions-log` · `open-questions` · `tasks` · `daily-summaries` ·
    `mvp-scope` · `skills-index` · המסמך הזה · `environments`.
- **כמה מאגרים:** תיקיית `docs/` יושבת רק במאגר אחד, מאגר התיעוד. עותק בכל מאגר יוצר סחיפה. בכל מאגר קוד מתקינים את הערכה
  עם `--docs-repo <נתיב-או-שם>`: בלי `docs/`, ו-`AGENTS.md` שלו מפנה למאגר התיעוד. החלטה שנוגעת במאגר קוד נרשמת ביומן של
  מאגר התיעוד, עם שם המאגר.
- `docs/00_Index.md` רושם כל מסמך עם הקטגוריה שלו.
- **קונפיגורציה (בכל פרויקט, לפי תוכנית המקור):** `configs/environments/` — שמות משתנים בלבד, בלי ערכים — ו-`configs/runtime/`.
  הטבלה המחייבת של הסביבות נשארת `docs/environments.md` (§8.4). במאגר קיים ממפים את המבנה הקיים ולא מזיזים.
- אם מודול `ai-product` מותקן: `prompts/` לפי `docs/prompts-and-json-governance.md`. במאגר קיים ממפים את המבנה הקיים
  לקטגוריות, ולא מזיזים קבצים.

### 5.3 החלטות ו-ADR

- **`docs/decisions-log.md` הוא הרשומה היחידה של החלטה.** כל החלטה מקבלת שורה עם קוד `<קידומת>-NNN` ורמת נעילה.
  ללא רמת נעילה — זו לא החלטה, זו שיחה.
- **ADR הוא נספח, ונכתב רק מעל סף:** גבול בין מאגרים או מערכות · ספק חיצוני · עלות · גבול נתונים ופרטיות.
  - שם הקובץ: `docs/adr/<קידומת>-NNN-<slug>.md`, **באותו מספר** של שורת היומן. אין מספור נפרד, כי סשנים מקבילים תופסים מספרים.
  - הפורמט: `docs/adr/ADR-TEMPLATE.md` והסקיל `arch-decision-record`. הפירוט ב-`docs/adr/README.md`.
- הסטטוס ורמת הנעילה המחייבת נמצאים ביומן. ADR שאושר אינו משתנה: שינוי = שורה חדשה ביומן ו-ADR חדש עם "מחליף את".
- לא ממירים החלטות ישנות ל-ADR, אלא אם בעל הפרויקט מבקש.

## 6. קוד, ענפים, PR ו-review

### 6.1 מדיניות לפי סוג השינוי (ברירת המחדל של הערכה)

| השינוי | איך מגיע ל-`main` | מי מאשר |
| :--- | :--- | :--- |
| **קוד:** שרת, לקוח, כלים, קונפיגורציית פריסה | ענף + PR | **אדם שלא כתב אותו**, גם כשסשן AI כתב את הקוד. בעבודה לבד: סבב ביקורת נפרד של `qa` ואישור בעל הפרויקט |
| **התנהגות המוצר:** מה המשתמש רואה או מקבל, prompts פעילים, כללי מדיניות בקוד | ענף + PR | **בעל הפרויקט** |
| קוד שמשנה גם התנהגות | ענף + PR | שניהם |
| **נתונים:** ריצות, תוצאות, רשימות, גרסה מועמדת שעוד לא קודמה | ישר ל-`main` | — |
| תיעוד בלבד | ישר ל-`main`. ⚠️ במאגר שבו push = deploy, זו פריסה (§3) | — |
| שחרור לייצור | רק מ-`main` אחרי מיזוג, לפי `docs/runbooks/release.md` | לפי רמת העצמאות ב-`AGENTS.md` |

- בעל הפרויקט רשאי לקבוע למאגר מסוים "push ישיר אחרי שלב ירוק" במקום ענף + PR. זו החלטה ביומן, והיא נרשמת בעמודה
  "מדיניות שינוי" ב-§3. ה-DoD חל בכל מקרה.

### 6.2 רמת העצמאות ומדיניות הענפים

רמת העצמאות (`AGENTS.md`) **אינה מבטלת** את המדיניות. היא קובעת רק אם ה-AI מחכה לאישור בעל הפרויקט בצעדים שהמדיניות מתירה.
הרשימה של מה שדורש אישור מפורש (`AGENTS.md` §9) וחוקי הברזל 3–4 חלים בכל רמה: העצמאות היא על ביצוע בתוך פריט שאושר, לא על החלטות.

| רמה | מה ה-AI עושה לבד בקוד |
| :--- | :--- |
| `strict` | שום דבר בלי אישור: כל commit וכל push מאושרים מראש |
| `balanced` | ענף, commits, PR והרצת regression. עוצר לפני merge ל-`main` ולפני push שהוא deploy |
| `autonomous` | גם merge ו-push אחרי שלב ירוק, כשה-DoD התקיים. PR שמחכה ל-review של אדם ממשיך לחכות לו. בעבודה לבד: האישור הקבוע של בעל הפרויקט, כפי שנרשם ביומן, הוא האישור. **האישור הקבוע מחליף review של קוד בלבד; שינוי התנהגות מוצר — תמיד אישור בעל הפרויקט.** סבב `qa` הנפרד נשאר חובה |

### 6.3 תבנית PR מינימלית

- משפט התנהגות לכל שינוי: מה המשתמש יראה אחרת.
- diff: של הקוד, או של הגרסה מול האב.
- המספרים של החבילה החינמית (§9.3).
- מה **לא** נמדד, ובמיוחד "לא נמדד בתשלום".
- נקודת חזרה: hash או מזהה גרסה.

**PR נדחה אם:** המאשר הוא הכותב · חסר "מה לא נמדד" · אין נקודת חזרה.

### 6.4 אכיפה

- עדיף להגן על ענף `main` בפלטפורמת ה-Git. אם הגנת ענף שוברת כלי שכותב נתונים ישר ל-`main`, האכיפה נעשית בכלל,
  ופותחים משימה לאכיפה טכנית.
- עד שיש אכיפה טכנית, סשן AI אינו ממזג קוד או התנהגות ל-`main` בעצמו, אלא לפי §6.2.

### 6.5 Prompts ו-JSON

- אם מודול `ai-product` מותקן, הכללים המלאים ב-`docs/prompts-and-json-governance.md`.
- הכללים של המקור, בשורה אחת: ב-Git · שמות ברורים · הפרדה בין active, deprecated ו-experimental · review ב-PR · תיעוד
  כל שינוי שמשפיע על התנהגות · **אין שינוי נסתר בזמן ריצה.**
- הגדרה שמשנה התנהגות בייצור בלי commit (מסך ניהול, פרופיל בממשק אדמין) נרשמת ביומן בכל שינוי (DoD סעיף 6).

### 6.6 סשנים מקבילים

- קוראים את **הזנב** של היומן, של השאלות ושל המשימות **מיד לפני** שמקצים מספר. עד שהמספר נקבע כותבים "(בהכנה)".
- מריצים `git diff --stat <path>` **רגע לפני** `git commit`, ומקמטים בנתיבים מפורשים, לא ב-`-a`.
- אין שני כותבים על אותו קובץ. סשן אחד לכל עץ עבודה (worktree).

## 7. משימות, ספרינט ובעלות

### 7.1 מקור המשימות

- המקור מוגדר ב-`AGENTS.md`. עם מודול `jira`: `docs/jira-workflow.md` (חיבור, עדכון אוטומטי, המעבר מ-`docs/tasks.md`).
  בלי המודול: `docs/tasks.md`, ומשימה חדשה מקבלת `T-NNN`.
- **מקור משימות משותף:** תיאור קצר, רק מה מבקשים ומה צריך להכריע. בלי סכומים, חשבונות, מזהים, טלפונים, שמות, טקסט משיחה
  וממצאי אבטחה מפורטים.
- **ה-AI לא מוחק פריטים ב-Jira, גם לא בבקשה מפורשת** — מחיקה בלתי הפיכה. פריט שנפתח בטעות: מי שיש לו הרשאת מחיקה מוחק
  (ה-AI יכול לפתוח לו את הפריט ולהראות איפה); בלי הרשאה — מנקים וסוגרים כ"נפתח בטעות". עבודה שאינה של הפרויקט לא נפתחת שם
  מלכתחילה. כתיבה שנחסמה ע"י מנגנון ההרשאות של הכלי — לא עוקפים דרך הדפדפן; בעל הפרויקט מבצע בממשק או מוסיף כלל הרשאה.
  הנוהל המלא: `docs/jira-workflow.md` §6 ו-§10.

### 7.2 הספרינט

**שבועי.** מטרה אחת · משימות בעדיפות · באגים מפורשים · חוב טכני לפי הצורך · משימת תיעוד כשהתנהגות או ארכיטקטורה משתנות ·
בעלים לכל משימה.

**איך זה מתיישב עם "פריט אחד בכל פעם, בסדר שבעל הפרויקט קובע":**
- בעל הפרויקט קובע את המטרה ואת סדר הפריטים ב-Planning. הסוכן הראשי ממליץ, והאחראי הטכני (אם יש כזה בטבלת הצוות) מביא את
  התלויות הטכניות.
- כל אדם וכל סשן מחזיקים **פריט אחד** ב-In Progress. זה גם המנעול בין סשנים מקבילים. ברמת `autonomous` מותרים כמה
  פריטים במקביל, כל אחד בסשן משלו, ובלי שני כותבים על אותו קובץ.
- חוק הברזל "כיוון אחד" = מטרת הספרינט.
- בפתיחת סשן ההמלצה היא "הפריט הבא בספרינט הפעיל".
- מטרת הספרינט נכתבת ב-`docs/project-status.md`, וגם בשדה המטרה במקור המשימות אם יש כזה.

**מה נכנס באמצע ספרינט:** באג בייצור, או פריט שבעל הפרויקט אמר במפורש שהוא דחוף. כל השאר הולך ל-backlog ול-Planning הבא.

### 7.4 בעלות

- ה-assignee הוא תמיד **אדם**: מי שמכוון את הסשן ומאשר את התוצאה, לפי טבלת הצוות ב-`AGENTS.md`. בעבודה לבד זה בעל הפרויקט.
- סשן AI מבצע, והוא אינו הבעלים. הסוכנים המקצועיים מייעצים, והם נכתבים בתיאור הפריט.

### 7.5 באגים

- באג שהגיע לייצור, או שאדם דיווח עליו, נפתח כפריט במקור המשימות. אם אין סוג Bug, משתמשים בסוג Task.
- **שדות:** סביבה · גרסה (hash או מזהה גרסה) · צעדי שחזור · צפוי מול בפועל · חומרה.
- **נסגר רק עם:** commit · בדיקה שנכשלת לפני התיקון ועוברת אחריו, או נימוק למה אי אפשר · אימות חי.
- באג שחבילת בדיקה תפסה לפני push נרשם בשורת היומן של השינוי, בלי פריט נפרד.

## 8. נתונים, לוגים, secrets, סביבות

### 8.1 כללי האחסון — מחייבים

| הכלל | מצב בפרויקט |
| :--- | :--- |
| קוד ב-Git | ⏳ |
| prompts ו-JSON ב-Git | ⏳ |
| קבצים שמשתמשים העלו — **לא** ב-Git | ⏳ |
| פלטים שנוצרו — **לא** ב-Git | ⏳ |
| secrets — **לא** ב-Git | ⏳ |
| וקטורים ו-chunks במאגר וקטורי, אם יש RAG (§8.5) | ⏳ |
| מצב ריצה (runtime state) במאגר נתונים מתאים, ולא בקבצים מקומיים מאולתרים | ⏳ |

**חריגים מוצהרים:** חריג נשאר רק עם נימוק ועם תנאי יציאה.

| מה | למה נשאר / מה הבעיה | תנאי יציאה |
| :--- | :--- | :--- |
| ⏳ למלא (לדוגמה: תוצאות ריצות בדיקה בגיט, כראיה לשחזור) | | |

### 8.2 לוגים ומזהה בקשה — כלל לקוד חדש

1. כותרת אחת לכל המערכת: `X-Request-Id`.
2. **רק שרת הקצה מייצר אותה:** UUID אקראי לכל בקשה. המזהה **לעולם לא נגזר** מלקוח, מסשן או מטלפון, ולעולם לא מתקבל מהדפדפן.
3. שירות פנימי מקבל את המזהה רק אם הוא תואם `^[\w-]{1,64}$`, ואחרת מייצר חדש. הוא מחזיר את המזהה בכותרת התשובה
   וב-`error.request_id`.
4. המזהה לא יוצא לספק חיצוני.
5. שורת לוג = אובייקט JSON אחד ל-stdout: `ts` (UTC) · `svc` · `rid` · `caller` · `method` · `route` (התבנית, לא הנתיב
   עם הערכים) · `status` · `ms` · `code` · `event`.

**אסור בלוג:**

| מה | הערה |
| :--- | :--- |
| טלפון מלא · קוד חד-פעמי (OTP) וכל קוד אימות · טוקן · cookie | טלפון ממוסך מותר, אם בכלל, רק בשורת הכניסה |
| מספר זהות או כל מזהה ממשלתי, **גם מגובב** | כשהמלח ידוע, הגיבוב הפיך |
| שם · מייל · שם קובץ שמשתמש העלה · תוכן מסמך או פלט · מונחי חיפוש בנתיב | |
| טקסט שיחה (גם של שאלות ל-API) · מזהה שיחה · מזהה משתמש בשורה של שיחה | |
| מפתחות · ערכים מוצפנים · פירוט שגיאה גולמי | פירוט גולמי מותר רק במסך ניהול מוגן |
| גוף בקשה "רק לדיבאג" | אין חריג |

**לא עושים:** ספק לוגים חיצוני בלי אישור (זה ספק חדש, חוק ברזל 1) · ספריית לוגים משותפת בין מאגרים, אם הארכיטקטורה אוסרת
קוד משותף.

### 8.3 secrets

1. ערך סודי יושב רק באחד משלושה מקומות: env בפלטפורמת הפריסה · `.env` מקומי (ב-gitignore) · תיקיית secrets מקומית מחוץ לגיט.
2. **בגיט מותר:** שם משתנה · sha256 של קוד אקראי באורך 80 ביט ומעלה · מזהה שאינו פרט כניסה. **אסור:** גיבוב של סיסמה, טלפון
   או מספר זהות.
3. בייצור, סוד חסר מפיל את השרת בעלייה. אין נפילה לברירת מחדל מקומית.
4. הסריקה לפני push מחפשת מפתחות **וגם** מידע אישי (`docs/data/README.md`).
5. מלח או pepper שאי אפשר להחליף מסומן ⛔ במפת הסודות (`docs/environments.md` §4).
6. ה-AI אינו קורא, מדפיס או מקליד ערך סודי. בעל הפרויקט מזין סודות בעצמו.

### 8.4 סביבות וקונפיגורציה

- **טבלה אחת** ב-`docs/environments.md`: סביבה × משתנה × איפה מוגדר × מי מגדיר. **שמות בלבד, בלי ערכים.**
- `.env.example` בכל מאגר, עם שמות והסברים בלבד.
- קובץ קונפיגורציית הפריסה (אם יש) הוא הקונפיגורציה של הייצור, ושינוי בו הוא שינוי ייצור.
- **בדיקת סחיפה** בין שלושה מקומות: מה שהקוד קורא מהסביבה, מה שמוגדר בפלטפורמת הפריסה, ומה שכתוב בטבלה.
- env אינו בגיט, ולכן יומן הקונפיגורציה (`docs/environments.md` §5) הוא ה-version control שלו.

### 8.5 RAG ומאגר וקטורי — רק כשיש צורך

- **המגבלות של המקור לשלב הראשון מחייבות:** use case אחד מוגדר היטב · ingestion וחילוץ טקסט דטרמיניסטיים · כללי chunking
  מוגדרים · תיעוד הקלט והפלט של ה-retrieval · בדיקת איכות ידנית.
- **בלי** retrieval רב-שלבי agentic · routing מורכב · שינוי prompts אוטונומי · re-ranking מורכב בקנה מידה גדול · retrieval נסתר.
- **"לתעד קלט ופלט" בתעבורת ייצור:** נרשמים מזהי קטעים, גרסת הקורפוס, ציונים וספירות. **לא טקסט.** טקסט נשמר רק בסביבת
  ניסוי או בארכיון מוגן.
- embeddings ומאגר וקטורי הם בדרך כלל ספק חדש, ולעתים בתשלום. לכן נדרש אישור פר-ספק (חוק ברזל 1) ו-ADR.

## 9. Definition of Done

### 9.1 משימה גמורה רק כאשר

1. **ב-Git.** יש commit (hash) בכל מאגר שנגעו בו. קוד מערכת נדחף ואומת חי, או מסומן "לא נפרס" עם סיבה.
2. **נבדק, ואפשר לבדוק שוב.** ה-regression לפי סוג השינוי (§9.2–9.3) עבר עם 0 נכשלים ו-0 "לא נבדק". **דילוג אינו הצלחה:**
   בדיקה שלא רצה, או שלא יכלה לרוץ, נספרת כ"לא נבדק" — כנכשלת, לא כעוברת. דילוג רשום בשמו נשאר "לא נבדק" — fail, עם משימה
   פתוחה (סעיף 3), והפריט לא נסגר כ-Done עד שהבדיקה רצה. חריג יחיד: בעל הפרויקט אישר את החריג במפורש, לפריט הזה, בשורה ביומן
   עם הנימוק — ההמלצה של `qa` נשארת fail, והמשימה נשארת פתוחה. אישור קבוע או רמת העצמאות אינם אישור לחריג כזה.
3. **אדום ידוע = משימה.** אין אדום קבוע בלי משימה פתוחה.
4. **אימות חי:** מקומי לפני push. אחרי push שהוא deploy, בדיקה חיה חינמית של מה שנגעו בו.
5. **תיעוד:** שינוי התנהגות או ארכיטקטורה → שורה ביומן, עם hash, הפקודות, המספרים, ומה **לא** נבדק. שינוי אחר אינו דורש שורה.
6. **קונפיגורציה:** שינוי env, קונפיגורציית פריסה או הגדרה במסך ניהול → שם המשתנה (לא הערך), השירות, מי שינה, והבדיקה
   שמוכיחה. הרישום נעשה ביומן ובטבלת הסביבות.
7. **בעלים:** אדם אחד הוא ה-assignee ואישר את התוצאה. הפריט עבר ל-Done עם שורת סיכום: מה נעשה, איזו בדיקה, מה התוצאה.
8. **מקור המשימות נקי:** אין בפריט סוד, מידע אישי, סכום או ממצא אבטחה מפורט.

### 9.2 "ניתן לשחזר או לבדוק" — לפי סוג השינוי

| סוג | ההוכחה |
| :--- | :--- |
| קוד מערכת | hash · החבילות של המאגר · חבילות חוצות-מערכות אם נגעו בחוזה, בשער (הרשאות וכניסה) או בחיבור · בדיקה חיה ברוחב 375 וקונסול נקי, אם יש ממשק · אחרי deploy: בדיקת health בכתובת הייצור ובדיקה חיה חינמית של מה שנגעו בו |
| prompt / JSON (מודול `ai-product`) | גרסה עם אב ו-hash · רשימת שינויים · החבילה החינמית · **"לא נמדד בתשלום"** כתוב במפורש, אלא אם אושרה ריצה בתשלום עם תקציב · אחרי שחרור: הייצור מגיש את ה-hash הצפוי. הפירוט ב-`docs/prompts-and-json-governance.md` |
| תיעוד בלבד | diff בלי קוד. ⚠️ במאגר שבו push = deploy, זה עדיין deploy (§3) |
| env / קונפיגורציה | שורה ביומן · שורה ביומן הקונפיגורציה (`docs/environments.md` §5) · בדיקה חיה שמוכיחה את השינוי |

### 9.3 regression מינימלי לפני push — בחינם

- **(א) תמיד:** החבילות של המאגר שנגעו בו · בדיקת סחיפה, אם קיימת · סריקת secrets ומידע אישי.
- **(ב) כשנגעו בחוזה, בשער או בקונפיגורציה:** גם הרצה מקומית של הזרימה הסטנדרטית מקצה לקצה, ובדיקת קונפיגורציה.
- **(ג) שינוי prompt או JSON:** החבילה החינמית של מודול `ai-product`.
- **אסור ב-regression:** SMS או מייל אמיתי · קריאה בתשלום למודל · ריצה מלאה בתשלום. אלה רצים רק בהחלטה מפורשת של בעל
  הפרויקט, עם תקציב.
- **פעם אחת, כשער:** החבילות רצות פעם אחת לפני push, ולא אחרי כל שלב. חבילה שסוכן דיווח עליה ירוק, עם מספרים, נחשבת.
  ביקורת אחת לכל פריט, ממוקדת בשינוי.

**הזרימה הסטנדרטית של הפרויקט:**
⏳ למלא: שורה אחת. לדוגמה: אורח → הרשמה → פעולת הליבה → תוצאה → המשתמש רואה סטטוס.
הפקודות: `docs/runbooks/local-setup.md` §3.

**חורים ידועים בכיסוי** (כל חור = משימה):
⏳ למלא: רשימה.

## 10. סדר העדיפויות — תוכנית לספרינטים הראשונים

שכבר קיים, ולא בונה אותו מחדש.

הסדר כאן שונה מהמקור: קודם בא מה שמאפשר לכל אחד לשחזר את המערכת, ו-prompts אחר כך. **עם מודול `ai-product` — סדר המקור:
פריט 4 (ארגון prompts ו-JSON) עולה לספרינט 1.** המקור נכתב למוצר שנשען על prompts, ושם זו ברירת המחדל הנאמנה.
