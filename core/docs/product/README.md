# docs/product — מה בונים, למי, ואיך זה נראה למשתמש

> כאן נמצא האפיון: מסעות משתמש, מסכים, נוסחים, קריטריוני קבלה וחבילות החלטה.
> ההיקף עצמו נמצא ב-`docs/mvp-scope.md`, וההחלטות ב-`docs/decisions-log.md`.

## מה נכנס

| מסמך | מה הוא עונה |
| :--- | :--- |
| `user-flow.md` / `journeys/` | מסע המשתמש מקצה לקצה, לכל סוג משתמש |
| `screens.md` | המסכים, המצבים שלהם (ריק, טעינה, שגיאה, הצלחה) והמעברים |
| `microcopy.md` | **מקור האמת לנוסחים** במוצר: קול המותג, מונחים, נוסחי כפתורים והודעות (הסקיל `microcopy-source-of-truth`) |
| `acceptance-<נושא>.md` | קריטריוני קבלה שאפשר לבדוק, לכל פיצ'ר |
| `test-plan.md` | תוכנית הבדיקות ומטריצת העקיבות (`spec-to-test-traceability`) |
| `<נושא>-decision-pack.md` | חבילת החלטה לבעל הפרויקט: האפשרויות, ההמלצה ומה דורש אישור |

## הכללים

- **כל פיצ'ר נבדק מול `docs/mvp-scope.md`** עם הסקיל `mvp-fit-check` לפני שנכתב לו אפיון.
- **מצבי קצה** (offline, timeout, כשל ספק, קוד שפג) מאופיינים עם הסקיל `edge-state-ux-spec`.
- **`microcopy.md` נוצר עם הנוסח הראשון.** ⏳ למלא: קול המותג בשלוש שורות: למי מדברים, באיזה טון, ומה אסור.
- ⚖️ **טקסט משפטי** (מדיניות פרטיות, תנאי שימוש, מסכי הסכמה) לא מנוסח כאן. כותבים placeholder מסומן בלבד, עד שיש נוסח מיועץ.
- **שדה שאוסף מידע אישי** עובר את הסקיל `privacy-data-check` לפני שהוא נכנס לאפיון.
- **אפיון אינו החלטה.** שינוי היקף, פיצ'ר מרכזי או שינוי מהותי בחוויה דורשים אישור של בעל הפרויקט ושורה ביומן.
- **קריטריון קבלה נכתב כך שאפשר לבדוק אותו:** מה עושים, ומה צריך לקרות. הסוכן `qa` ממפה אותו לבדיקה (`spec-to-test-traceability`).
