# docs/adr — רשומות החלטה ארכיטקטונית

> ADR הוא **נספח** לשורה ב-`docs/decisions-log.md`, ולא תחליף לה. היומן הוא הרשומה היחידה של החלטה.
> הכללים המלאים: `docs/engineering-operating-model.md` §5.3.

## מתי כותבים ADR — רק מעל הסף

כותבים ADR כשההחלטה חוצה לפחות אחד מאלה:

| הסף | לדוגמה |
| :--- | :--- |
| **גבול בין מאגרים או מערכות** | מי מדבר עם מי, חוזה חדש בין שירותים, העברת אחריות לשירות אחר |
| **ספק חיצוני** | חיבור ספק אמיתי, החלפת ספק, יציאה מ-Mock |
| **עלות** | כל בחירה שעולה כסף, עכשיו או בהמשך |
| **גבול נתונים ופרטיות** | איפה נשמר מידע אישי, מי רואה אותו, כמה זמן, מה יוצא לספק |

כל החלטה אחרת היא שורה ביומן בלבד.

## השם והמספר

- `docs/adr/<קידומת>-NNN-<slug>.md`. הקידומת והמספר הם **של שורת היומן** (לדוגמה `ABC-014-payments-provider.md`).
  אין מספור נפרד ל-ADR.
- `<slug>`: באנגלית, אותיות קטנות ומקפים, עד חמש מילים.
- סשנים מקבילים תופסים מספרים. קוראים את הזנב של היומן **מיד לפני** שמקצים מספר.

## התהליך

1. הסוכן המקצועי הרלוונטי (בדרך כלל `system-architect` או `backend`) מנתח עם הסקיל `arch-decision-record`, ומחזיר בלוק ADR לצ׳אט.
2. הסוכן הראשי מאחד ומציג לבעל הפרויקט: הקשר, חלופות, הכרעה מוצעת, השלכות ורמת נעילה מוצעת.
3. **רק אחרי אישור:** הסוכן הראשי כותב את שורת היומן ואת קובץ ה-ADR מתוך `ADR-TEMPLATE.md`, באותו commit.
4. ההחלטות שמחכות לאישור נשארות בצ׳אט או ב-`docs/open-questions.md`. אין ADR "בהמתנה" בתיקייה.

כל ADR עובר את הסף, ולכן הוא **תמיד** דורש אישור של בעל הפרויקט, בכל רמת עצמאות. ספק, עלות, מבנה מערכת ופרטיות
נמצאים ברשימת "מה דורש אישור מפורש" ב-`AGENTS.md`.

## הכללים

- **הסטטוס ורמת הנעילה המחייבת נמצאים ביומן.** ב-ADR נשמרים ההקשר, החלופות וההשלכות.
- **ADR שאושר אינו משתנה.** שינוי = שורה חדשה ביומן ו-ADR חדש עם "מחליף את: `<קידומת>-NNN`". בשורה הישנה ביומן מוסיפים
  "הוחלף ב-…".
- **חלופה אחת אינה ADR.** תמיד לפחות שתי חלופות, כולל "לא לעשות כלום" כשזה רלוונטי.
- **חובה לכתוב "מה לא נבדק".** אם הכול נבדק, כותבים מה נבדק ואיך.
- בחירה עם השלכות עלות אינה עולה מעל 🔧 בלי שבעל הפרויקט ראה את המחיר.
- לא כותבים ADR רטרואקטיבי להחלטות ישנות, אלא אם בעל הפרויקט מבקש.
