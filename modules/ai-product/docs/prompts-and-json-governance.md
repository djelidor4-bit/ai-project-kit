# ממשל prompts ו-JSON

> **מה זה:** הכללים של מודול ai-product. הם חלים על מוצר שההתנהגות שלו נקבעת ב-prompts, בדוגמאות, בקונפיגורציית מודל
> ובחוזי JSON שנשלחים למודל שפה.
> מבוסס על 'תוכנית תפעול הנדסית ל-MVP'. המקור: הפרקים "ממשל עבור Prompts ו-JSON"
> ו"תוכנית RAG", בהתאמה כללית לכל פרויקט.
> **קשור:** `docs/engineering-operating-model.md` (DoD, regression, לוגים) · `docs/environments.md` · `docs/decisions-log.md` ·
> הסקילים `privacy-data-check`, `arch-decision-record`, `spec-to-test-traceability`.

---

## 1. בשורה אחת

prompts ו-JSON הם קוד. הם נשמרים בגיט, בגרסאות שאינן משתנות, ועוברים review. הם משתחררים רק עם הוכחה חינמית ונקודת חזרה.
כל מה שמשנה את מה שה-AI אומר צריך אישור של בעל הפרויקט.

## 2. מה נחשב נכס AI

כל המסמך חל על הנכסים האלה:

| נכס | דוגמאות |
| :--- | :--- |
| הוראות מערכת | system prompt, הוראות לכל שלב |
| דוגמאות | few-shot, תשובות לדוגמה |
| מדיניות | ביטויים אסורים וביטויי חובה, placeholders, כללי הסלמה |
| קונפיגורציית מודל | מזהה מודל, temperature, max tokens, stop |
| חוזי JSON | סכמות של קלט ופלט, הגדרות של tools ו-functions |
| קורפוס ו-retrieval | גרסת הקורפוס, כללי chunking, קטלוג המקורות |
| נוסחים שכתובים בקוד | ביטויי בטיחות ותבניות תשובה בקוד. **גם הם התנהגות** |

## 3. הכללים מתוכנית המקור, מחייבים

1. קובצי prompt נשמרים ב-Git.
2. כללי naming ברורים.
3. הפרדה בין נכסים פעילים, deprecated ו-experimental.
4. review לשינויי prompt דרך pull request.
5. תיעוד של כל שינוי שמשפיע על ההתנהגות.
6. אין שינוי נסתר בזמן ריצה.

## 4. המבנה

בוחרים אחת משתי האפשרויות בתחילת הפרויקט, ורושמים החלטה ביומן.

**אפשרות א׳: תיקיות לפי סטטוס (המבנה המקורי).**
```
prompts/
  active/
  deprecated/
  experiments/
configs/
  environments/   ← שמות משתנים בלבד, בלי ערכים
  runtime/
```

**אפשרות ב׳: חבילות בגרסאות ומצביע.** מומלצת כשמשנים את ה-prompts לעתים קרובות.
```
prompts/
  versions/
    p-0001.json
    p-0002.json
  current.json        ← מצביע לגרסה הפעילה
  promotions.jsonl    ← היסטוריית הקידומים
```
באפשרות ב׳ הסטטוס נגזר מהמצביע:
- **פעיל:** הגרסה ש-`current.json` מצביע עליה.
- **experimental:** כל גרסה שלא קודמה. היא **מועמדת**.
- **deprecated:** גרסה שהייתה פעילה בעבר. היא נשמרת כהיסטוריה וכנקודת חזרה.

⚠️ **לא מזיזים קבצים אחר כך רק בשביל שם של תיקייה.** כשכלים, בדיקות והיסטוריה תלויים בנתיב, הזזה שוברת אותם. במקום להזיז,
ממפים: טבלה ב-`docs/architecture/` שמראה איך המבנה שלכם מתאים לסטטוסים.

**חבילת גרסה (אפשרות ב׳):**
```json
{
  "id": "p-0007",
  "parent": "p-0006",
  "created": "YYYY-MM-DD",
  "author": "<אדם, או סשן AI ושם האדם שכיוון אותו>",
  "changes": ["משפט התנהגות אחד לכל שינוי"],
  "model": { "id": "<מזהה מודל מלא>", "temperature": 0.2, "max_tokens": 1024 },
  "corpus": "<גרסת הקורפוס, או null>",
  "system": "…",
  "examples": [],
  "policy": {},
  "hash": "<sha256 של התוכן הקנוני, בלי השדה hash>"
}
```

**המצביע:**
```json
{ "active": "p-0007", "since": "YYYY-MM-DD", "decision": "<קוד ההחלטה ביומן>" }
```

**היסטוריית הקידומים:** שורה לכל קידום, עם התאריך, מי קידם, מאיזו גרסה לאיזו, קוד ההחלטה ומספרי החבילה החינמית.

**כללי naming וגרסאות:**
- לכל גרסה יש מזהה רץ (`p-NNNN`). כל גרסה חוץ מהראשונה מצביעה על אב. ה-hash מחושב על תוכן קנוני.
- **גרסה לא משתנה אחרי שנשמרה.** תיקון הוא גרסה חדשה עם אב.
- **המודל נעול בגרסה.** החלפת מודל, או גרסת מודל, היא גרסה חדשה עם הערכה מחדש. תוצאת בדיקה חלה רק על המודל שנבדק. משתמשים
  במזהה מודל מלא, לא בכינוי מתגלגל כמו `latest`.
- גרסה שנוצרה בסביבה משותפת או בענן היא תמיד **מועמדת**. רק קידום מאושר הופך אותה לפעילה.

## 5. מה עובר PR, ומי מאשר

| השינוי | איך הוא מגיע ל-`main` | מי מאשר |
| :--- | :--- | :--- |
| **התנהגות:** קידום גרסה (הזזת המצביע), נוסחי בטיחות בקוד, כל מה שמשנה את מה שה-AI אומר | ענף + PR. כשבעל הפרויקט מקדם בעצמו בכלי שרושם את הקידום בהיסטוריה, הקידום הוא האישור | **בעל הפרויקט** |
| **קוד:** אפליקציה, כלים, קונפיגורציית פריסה | ענף + PR | **אדם שלא כתב אותו**, גם כשהקוד נכתב בסשן AI. בעבודה לבד: סבב ביקורת נפרד של `qa`, ואחריו אישור בעל הפרויקט |
| קוד שמשנה גם התנהגות | ענף + PR | שניהם |
| **נתונים:** ריצות הערכה, הערות, יומנים, גרסה מועמדת חדשה | ישר ל-`main`, אם הפרויקט מאפשר זאת | — |
| תיעוד בלבד | ישר ל-`main` | — |
| שחרור לייצור | רק בהנחיה, ורק מ-`main` אחרי מיזוג | בעל הפרויקט |

- **סשן AI לא מקדם גרסה ולא מזיז את המצביע בקומיט ל-`main`. הכלל חל בכל רמות העצמאות.** הסשן בונה מועמדת, מריץ את
  החבילה החינמית ומגיש PR. בעל הפרויקט מקדם את הגרסה, או מאשר במפורש את הקידום.
- **תבנית PR מינימלית:**
  - משפט התנהגות לכל שינוי.
  - diff של הגרסה מול האב, או diff של הקוד.
  - המספרים של החבילה החינמית.
  - מה **לא** נמדד, ובמיוחד "לא נמדד בתשלום".
  - נקודת חזרה: מזהה גרסה או hash.
- **PR נדחה אם:** המאשר הוא מי שכתב · חסר "מה לא נמדד" · אין נקודת חזרה.
- **אכיפה:** עדיף להגן על הענף. אם הגנה על `main` שוברת כלים שכותבים נתונים ישירות, האכיפה נעשית לפי הכלל, והעניין נרשם
  כחוב טכני עד שתהיה אכיפה טכנית.

## 6. אין שינוי נסתר בזמן ריצה

- **כל מה שמשנה את מה שה-AI אומר בייצור עובר דרך גרסה בגיט.**
- **ממשק שמשנה ייצור בלי commit:** למשל לוח ניהול שעורך prompt, פרופיל מודל, מפתח או חיבור. כל שינוי בו נרשם ביומן ובטבלת
  השינויים של `docs/environments.md`, עם:
  - שם השדה או המשתנה (לא הערך).
  - השירות.
  - מי שינה.
  - הבדיקה שמוכיחה את השינוי.
- **מטמון ו"זיכרון תשובות"** שמגישים תשובה בלי לעבור במודל מתועדים ונבדקים בחבילה, והגרסה שלהם נרשמת בשחרור.
- **תיקון מיידי בממשק** (כשמשתמש פנימי מתקן תשובה) לא משנה גרסה. התיקון נאסף כנתון למועמדת הבאה.
- **אסור:**
  - prompt שמשנה את עצמו, או שינוי אוטונומי של prompts.
  - ניסוי A/B נסתר בייצור.
  - retrieval נסתר. צריך להיות אפשר לשחזר מהלוג מה המודל קיבל: הגרסה ומזהי הקטעים.

## 7. בדיקה ושחרור

### 7.1 מגדירים מראש, במספרים, מה זה "עובד"
לפני שבונים מועמדת, כותבים את הרף. דוגמאות: אחוז מעבר על קבוצת השאלות, אפס ביטויים אסורים, זמן תגובה ב-p90, עלות לשיחה.
כשהרף מוגדר מראש, ההחלטה לשחרר, או לשלם על מדידה, לא נשענת על תחושת בטן.
⏳ למלא: הרף של הפרויקט, ואיפה הוא נשמר (מומלץ: `docs/product/`).

### 7.2 החבילה החינמית (לפני כל PR של התנהגות)
- החבילה רצה בלי קריאה למודל בתשלום, ובודקת:
  - נוסח: ביטויים אסורים, ביטויי חובה, placeholders שלא מולאו.
  - תקינות JSON מול הסכמה.
  - כללי מדיניות על תשובות שמורות או מוקלטות.
  - diff מול האב.
  - זרימה מלאה מול מודל מדומה (Mock).
- התוצאה הנדרשת: 0 נכשלים ו-0 "לא נבדק". **דילוג אינו הצלחה.**
- ⚠️ **מבחן חינמי מתגמל התאמת-יתר.** אם מכוונים את הגרסה לפי אותה קבוצת שאלות שבודקת אותה, הציון עולה והאיכות לא.
  שומרים קבוצת hold-out שלא משמשת לכוונון.

### 7.3 בדיקה בתשלום
- **רק באישור מפורש של בעל הפרויקט, עם תקציב (סכום) שנקבע לפני ההרצה.** אישור לריצה אחת אינו אישור לריצה הבאה.
- ההצעה לבעל הפרויקט כוללת: מה הבדיקה תמדוד, כמה קריאות, עלות משוערת (עלות לקריאה מריצה קודמת × מספר הקריאות), ומה ייחשב הצלחה.
- אם בכלי יש תקרת הוצאה, מעלים אותה רק לריצה הזו ומחזירים אותה מיד אחריה.
- אחרי הריצה רושמים ביומן את העלות בפועל ואת התוצאות.
- אם בעל הפרויקט עצר הוצאות, לא מריצים שום דבר בתשלום עד הודעה חדשה. גם לא "בדיקה קטנה".
- ה-regression לפני push **אף פעם** לא קורא למודל בתשלום.

### 7.4 רשימת שחרור
- [ ] מזהה גרסה, אב ו-hash · רשימת שינויים עם משפט התנהגות לכל שינוי
- [ ] גרסת הקורפוס, אם יש retrieval
- [ ] החבילה החינמית: 0 נכשלים ו-0 "לא נבדק", והמספרים כתובים
- [ ] בדיקת הנוסח עברה
- [ ] כתוב במפורש **"לא נמדד בתשלום"**, או שיש ריצה בתשלום שאושרה (תקציב, עלות בפועל, תוצאות)
- [ ] נקודת חזרה: מזהה הגרסה הקודמת
- [ ] בעל הפרויקט אישר את ההתנהגות, וה-PR מוזג
- [ ] אחרי השחרור: בדיקה חיה וחינמית מראה בייצור את מזהה הגרסה ואת ה-hash הצפויים
- [ ] שורה ביומן: מה השתנה, הפקודות והמספרים, ומה **לא** נבדק

### 7.5 חזרה לאחור
הזזת המצביע לגרסה קודמת היא שחרור לכל דבר: אישור, בדיקה חיה ושורה ביומן. בתקלה בייצור, בעל הפרויקט מאשר את החזרה במשפט
אחד, והבדיקות והתיעוד נעשים מיד אחריה.

## 8. לוגים של קריאות למודל

- כל קריאה נרשמת בשורת JSON אחת: `ts` · `svc` · `rid` · `prompt_version` · `model` · `tokens_in` · `tokens_out` · `ms` · `status` ·
  `code` · `cost_estimate`.
- **אסור בלוג, לפחות** (הרשימה המלאה: `docs/engineering-operating-model.md` §8.2):
  - טקסט השיחה, גם הקלט וגם הפלט.
  - טקסט ה-prompt כשהוא כולל קלט של משתמש.
  - תוכן מסמך.
  - מזהה משתמש, טלפון, מייל או שם.
  - מפתחות.
- מהודעה רגישה (מצוקה, מידע רפואי) לא נרשם שום דבר מעבר לשורה הטכנית.
- **retrieval:** נרשמים מזהי הקטעים, גרסת הקורפוס, הציונים והספירה. לא נרשם טקסט.
- מזהה הבקשה (`X-Request-Id`) **לא נשלח** לספק המודל.
- טקסט לצורכי הערכה נשמר רק במקום שהוחלט עליו במפורש, למשל סביבת מעבדה או ארכיון, עם החלטה ביומן ובדיקת `privacy-data-check`.
- **שליחת טקסט של משתמש לספק מודל היא חיבור לספק חיצוני אמיתי.** היא דורשת אישור פר-ספק ובדיקת `privacy-data-check`. נוסח
  הפרטיות מסומן ⚖️ ונשאר placeholder עד שיש נוסח מיועץ.

## 9. retrieval (RAG): רק כשצריך

לפי סדר העדיפויות בתוכנית המקור, RAG מגיע אחרי שהזרימה מתועדת, הסביבה מקומית ושחזירה, וה-prompts מסודרים.

**שלב 1, מינימלי ומכוון:**
1. בוחרים use case אחד בעל ערך גבוה.
2. מגדירים כללי ingestion למסמכים.
3. מחלצים טקסט באופן דטרמיניסטי.
4. מגדירים כללי chunking.
5. מייצרים embeddings.
6. שומרים את ה-chunks והמטא-דאטה במאגר וקטורי.
7. שולפים chunks מתאימים לשלבי prompt מוגדרים.
8. מתעדים את הקלט והפלט של ה-retrieval: מזהים, לא טקסט (§8).
9. בודקים את האיכות ידנית.

**לא בגרסה הראשונה:**
- multi-stage agentic retrieval.
- routing מורכב.
- שינוי prompts אוטונומי.
- re-ranking מורכב בקנה מידה גדול.
- retrieval נסתר.

**כללים נוספים:**
- embeddings ומאגר וקטורי הם ספק חדש, ולעתים בתשלום. לכן נדרשים אישור פר-ספק ו-ADR, כי השינוי חוצה את הסף של ספק, עלות
  ופרטיות (`docs/adr/README.md`).
- **הקורפוס מנוהל בגרסאות.** גרסת הקורפוס נרשמת בחבילת הגרסה.
- **מזהי הקטעים יציבים.** שינוי בפרסר או ב-chunking יוצר גרסת קורפוס חדשה: בונים את האינדקס מחדש ומריצים שוב את החבילה.
  שינוי במזהי הקטעים הוא שינוי התנהגות.

## 10. Definition of Done לשינוי prompt או JSON

נוסף על ה-DoD הכללי ב-`docs/engineering-operating-model.md`:
- מזהה גרסה, אב ו-hash · רשימת שינויים · גרסת קורפוס, אם יש.
- המספרים של החבילה החינמית: 0 נכשלים ו-0 "לא נבדק".
- כתוב במפורש **"לא נמדד בתשלום"**, או שיש ריצה בתשלום שאושרה ותועדה.
- אחרי השחרור: בדיקה חיה מראה את ה-hash הצפוי.
- שורה ביומן, עם מה **לא** נבדק.

## 12. מלכודות

- "רק שיניתי מילה ב-prompt" — גם זה שינוי התנהגות, וצריך PR ואישור.
