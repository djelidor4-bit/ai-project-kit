# הנחיות Frontend מול API — Contract-First ו-Mock-First

> המסמך הזה מגדיר איך בונים ממשק מול API שעדיין מתייצב: לפי חוזה כתוב, מול Mock, ובלי לפנות לשרת אמיתי מהדפדפן עד שהוחלט.
> מבוסס על 'תוכנית תפעול הנדסית ל-MVP' — ועל מסמך הנחיות ה-Frontend/API שנלווה אליה.

## בקצרה
1. מגדירים **חוזה API** ברור: endpoints, סכמות בקשה ותגובה, קודי שגיאה.
2. בונים את הממשק מול **Mock** שמחזיר בדיוק את צורת החוזה.
3. בהמשך מחברים את השרת האמיתי **מאחורי אותו חוזה** ומאמתים מולו — בלי שהממשק משתנה.

מה שלא ברור במסמך הזה או בחוזה — **שואלים, לא מנחשים** (`docs/open-questions.md`).

## כללים גלובליים
1. **אין פנייה ישירה מהממשק לשרת ייצור או staging** בשלב ה-Mock. אין כתובות שרת אמיתיות בקוד הממשק.
2. **Contract-first.** רכיבים נשענים על הצורות שבחוזה — לא על JSON מאולתר. שדה שאינו בחוזה אינו קיים.
3. **Mock-first.** לקוח Mock (או שרת Mock) מחזיר תגובות ריאליסטיות לפי החוזה. Mock "יצירתי" עם שדות נוספים — אסור.
4. **מודעות לסביבה.** מעבר בין מצב Mock למצב API אמיתי נעשה **בקונפיגורציה בלבד** (משתנה סביבה לכתובת הבסיס), לא בשינוי קוד.
5. **טיפול בשגיאות.** לא מניחים שכל תגובה היא 200. כל רכיב מטפל בשגיאת אימות (4xx), שגיאת שרת (5xx), מצב ריק ומצב "בעיבוד".
6. **תיעוד.** לכל זרימה מרכזית בממשק כתוב באילו endpoints היא משתמשת. צריך endpoint שאינו ברשימה — מעלים לדיון לפני שבונים.
7. **חוזה משתנה רק במקום אחד.** שינוי חוזה עובר דרך מסמך החוזה (`backend` הבעלים, `frontend` הצרכן) — לא בתיאום צדדי. שינוי חוזה מול מערכת חיצונית דורש אישור בעל הפרויקט.

## כתובת בסיס וסביבות
- כל קריאות ה-API עוברות דרך **כתובת בסיס אחת שניתנת להגדרה**. מקומית ובבדיקות — כתובת ה-Mock.
- שם המשתנה ומה כל סביבה מצביעה עליו נרשמים ב-`docs/environments.md` — **בשם המשתנה, לעולם לא בערך סודי**.
- דוגמאות לשם המשתנה (לדוגמה בלבד, לפי ה-framework):

| Framework | איפה מגדירים |
| :--- | :--- |
| React / Vite · Vue / Vite | `VITE_API_BASE` |
| Angular | `environment.apiUrl` |
| JS נקי | קבוע `API_BASE` בקובץ קונפיגורציה אחד |

⏳ למלא: שם המשתנה בפרויקט וכתובת ה-Mock המקומית.

**אסור בקוד הממשק:** מפתחות API, טוקנים של ספקים, כתובות פנימיות של שרתים. מה שנשלח לדפדפן — ציבורי.

## מצבי תגובה שכל רכיב מטפל בהם
| מצב | מה הממשק עושה |
| :--- | :--- |
| 200 / 201 | מציג תוצאה; ב-201 — מעדכן את הרשימה בלי רענון מלא |
| 202 (התקבל, בעיבוד) | מצב "בעיבוד" מפורש + בדיקת סטטוס חוזרת (ראו פעולות ארוכות) |
| ריק (200 עם רשימה ריקה) | מצב ריק מאופיין: מה זה אומר ומה הצעד הבא — לא מסך לבן |
| 400 / 422 (אימות) | שגיאה ליד השדה, בניסוח מתוך מקור הנוסחים — לא הודעת שרת גולמית |
| 401 / 403 | חזרה לכניסה או הודעת הרשאה — בלי לחשוף אם המשאב קיים |
| 404 | "לא נמצא" עם דרך חזרה |
| 429 | הודעת "נסה שוב בעוד…" ונטרול זמני של הפעולה |
| 5xx · timeout · offline | הודעה כללית + ניסיון חוזר; הנתונים שהמשתמש הקליד נשמרים |

המצבים ונוסחיהם — לפי הסקילים `edge-state-ux-spec` ו-`microcopy-source-of-truth`, לא מומצאים פר-מסך.

## פעולות ארוכות (עיבוד ברקע)
הדפוס המומלץ: `POST` שמתחיל פעולה מחזיר **202** עם מזהה וסטטוס `processing`; הממשק בודק `GET` סטטוס במרווחים (או מקבל אירוע), ומציג `processing` → `ready` או `error`.
- הסטטוסים הם **רשימה סגורה בחוזה** (enum) — הממשק לא מנחש סטטוס חדש.
- למרווח הבדיקה יש תקרה, ולמצב "בעיבוד" יש מגבלת זמן שאחריה מוצגת הודעה.
- רענון הדף באמצע עיבוד מחזיר את המשתמש לאותו מצב.

## קטלוג ה-endpoints — תבנית
⏳ למלא: מסמך החוזה המלא של הפרויקט (מומלץ ב-`docs/architecture/`), עם גרסה (למשל v0.1).

לכל endpoint: שיטה · נתיב · בקשה · תגובות (כולל שגיאות) · מי צורך אותו בממשק.

לדוגמה (משאב גנרי `items` — דוגמה בלבד, לא חוזה):

```text
POST /api/v1/items            → 201 { id, title, status: "draft|processing|ready|error", createdAt }
GET  /api/v1/items?status=    → 200 [ { id, title, status, createdAt, updatedAt } ]
GET  /api/v1/items/{id}       → 200 { ...פרטים } · 404
POST /api/v1/items/{id}/run   → 202 { id, status: "processing", startedAt }
GET  /api/v1/items/{id}/run   → 200 { status: "processing|ready|error", issues: [ { code, message, severity } ] }
```

- כל התאריכים ב-ISO-8601. שדה שיכול להיות ריק מסומן במפורש (`string | null`).
- שגיאות בצורה אחידה (למשל `{ code, message }`); הממשק מציג לפי `code`, לא לפי `message`.

## אסטרטגיית Mock
- ה-Mock בנוי **מהחוזה**, ומכסה: מסלול תקין · כל מצבי השגיאה · מצב "בעיבוד" · מצב ריק.
- ה-Mock לא סוטה מהחוזה. כשהחוזה משתנה — ה-Mock משתנה באותו שינוי.
- נתוני ה-Mock מומצאים וגנריים: **בלי מידע אישי אמיתי** (שמות, טלפונים, מזהים, מסמכים), גם לא "רק לבדיקה".
- Mock של ספק חיצוני נשאר ברירת המחדל מקומית ובבדיקות; ספק אמיתי — רק באישור פר-ספק.

## מזהה בקשה, לוגים ופרטיות בצד הלקוח
- `X-Request-Id` **נוצר רק בשרת הקצה** — הממשק לא מייצר אותו ולא גוזר אותו ממשתמש, סשן או טלפון. אם השרת מחזיר אותו, מותר להציג אותו בהודעת שגיאה ככלי לתמיכה.
- לא כותבים לקונסולה או ללוג מצד הלקוח — לפחות: טלפון מלא · קודי אימות, טוקנים ו-cookies · מזהה ממשלתי (גם מגובב) · שם · מייל · שם קובץ ותוכן מסמך · טקסט שיחה · מפתחות · גוף בקשה. הרשימה המלאה: `docs/engineering-operating-model.md` §8.2.
- מידע אישי לא עובר ב-URL או ב-query string.
